# Принципы модульной декомпозиции

Линза агента `architecture-review`. Источник идей — Udi Dahan и Particular Software (Services
как автономные бизнес-возможности, Composite UI). Здесь — переложение на одно приложение в одном
процессе: «сервис» = логический бизнес-модуль, не процесс и не сетевой эндпоинт.

Номера P* — для ссылок из отчёта. Признаки в коде Unity, LeoEcs и DOTS — `UNITY-SMELLS.md`. Новый пункт — следующим свободным номером, старые не
перенумеровываются.

## 1. Что такое модуль

**P1. Модуль = бизнес-возможность, а не технический слой.** Граница проходит там, где меняются
правила и данные, которые меняются вместе. «Repositories», «Services», «Managers», «UI» — слои, не
модули. Модуль может включать свой кусок UI, свои данные, свою логику и инфраструктуру.

**P2. Модуль — единственный технический владелец своих данных.** Пишет их только он. Остальные
знают о них лишь идентификатор (`ItemId`, `QuestId`) и события. Два модуля, которые пишут одно
поле, — одна ответственность, размазанная надвое, или граница проведена не там.

**P3. Одна «сущность» — разные данные в разных модулях.** Предмет: название и иконка — у
каталога, цена — у магазина, количество — у инвентаря, урон — у боя. Общий класс `Item` со всеми
полями сразу — признак декомпозиции по существительному, а не по возможности.

**P4. Сущностные «сервисы» — антипаттерн.** `PlayerService`, `ItemService`, `DataManager` с CRUD
над общей моделью собирают все возможности, касающиеся существительного. Каждая новая фича
расширяет один и тот же класс.

**P5. Инфраструктура — отдельная техническая сторона (IT/Ops у Dahan).** Сейв, сеть, SDK
платформы, аналитика, логирование, загрузка ассетов обслуживают модули, но бизнес-правил не
содержат и чужими данными не владеют.

## 2. Связи между модулями

**P6. Знать минимум.** Модуль ссылается на чужой контракт (событие, интерфейс запроса, id), а
не на конкретный класс, поля или внутреннее состояние. Чтение чужих полей напрямую — скрытая
зависимость от формы данных.

**P7. Событие лучше команды-запроса.** «Произошло X» (`QuestCompleted`) позволяет другим
реагировать, не делая источник зависимым от них. Когда источник сам вызывает награду, аналитику,
ачивку и UI — он знает всех получателей, и каждый новый получатель правит источник.

**P8. Временная связанность.** Модуль, который не может выполнить свой сценарий, пока синхронно
не опросит три других, связан с ними по времени и по форме ответа. Нужное для решения он держит
у себя (копия по событию) или делегирует решение владельцу.

**P9. Совместное изменение — главный тест границы.** Если по истории изменений фича в A почти
всегда трогает файлы B и C, логически это один модуль или граница проведена неверно.

**P10. Заявленная граница ≠ фактическая.** Папки, asmdef, namespaces, интерфейсы и DI ничего не
доказывают. Учитываются только реальные ссылки, кто пишет данные и поток данных.

## 3. UI и Composite UI

**P11. Один экран — композиция многих модулей.** Экран героя показывает уровень (прогрессия),
снаряжение (инвентарь), цену улучшения (экономика). Каждый модуль даёт свой виджет или свой
кусок ViewModel; экран только раскладывает их по слотам и знает общий id.

**P12. UI не определяет границы.** Нельзя заводить модуль, модель или сервис только потому, что
данные рядом на экране, относятся к одному игроку или персонажу. Признаки: «HUDData»,
«ProfileModel», «MainScreenService», ViewModel, собирающая данные из пяти сервисов и считающая
на них правила.

**P13. Действие на экране уходит владельцу.** Кнопка «купить» вызывает модуль магазина;
списание валюты — реакция экономики на событие или команда её контракту. Логика, которая решает,
можно ли купить, в View или Presenter экрана — правила, утёкшие в UI.

**P14. Branding/композиция отдельно от данных.** Общий layout, стили, навигация — отдельная
техническая сторона, которая не знает бизнес-данных.

## 4. Устройство модуля изнутри

**P15. Четыре уровня ответственности:** бизнес-правила и состояние; оркестрация сценария
(application logic); инфраструктура; presentation. Не обязательно четыре папки — обязательно не
перемешивать их в одном объекте.

**P16. Зависимости направлены к правилам.** Правила не знают про сейв, SDK, `MonoBehaviour`,
UI, сцену. Инфраструктура и presentation зависят от правил, не наоборот.

**P17. Оркестрация не содержит правил.** Сценарий «завершить уровень» вызывает: начислить,
сохранить, показать. Решение «сколько начислить» — в правилах. Расчёты в сценарии = правила,
которые невозможно переиспользовать и проверить отдельно.

**P18. Правило живёт в одном месте.** Одна и та же проверка (хватает ли валюты, открыта ли
фича) в View, в сервисе и в обработчике сейва — три копии, которые разойдутся.

**P19. Объект с избыточными обязанностями.** Признак — список причин для изменения длиннее
одной: «меняется, когда меняется баланс, формат сейва и анимация окна».

## 5. Что не считается находкой

- Отсутствие слоёв в маленьком модуле, где правила тривиальны.
- Прототип, плеебл, геймджем — если так записано в `CLAUDE.md` проекта.
- Общие value-типы без поведения (`ItemId`, `Currency` как enum) — общий язык, не общая модель.
- Прямой вызов внутри одного модуля.
- Стиль, нейминг, локальные code smells.

## 6. Направления исправления (словарь)

- **Передать владение** — данные и правило переезжают к модулю, который за них отвечает; у
  остальных остаётся id и подписка.
- **Разрезать модуль** — по данным и причинам изменения, не по размеру файла.
- **Заменить общую модель** — каждый модуль хранит своё по общему id; сейв — секциями модулей.
- **Событие вместо вызова** — источник публикует факт, получатели подписываются.
- **Композиция экрана** — каждый модуль даёт виджет/ViewModel-вклад, экран-хост только
  раскладывает.
- **Выделить сценарий** — оркестрация в отдельный объект, правила вниз, инфраструктура за
  интерфейсом, который определяет модуль.
