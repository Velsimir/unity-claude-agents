# Как нарушения границ выглядят в Unity

Дополнение к `PRINCIPLES.md` для агента `architecture-review`. Каждый пункт: признак → где искать
→ какой принцип нарушен. Номера U* — для ссылок из отчёта, новые дописываются в конец.

## Данные и владение

**U1. Общий `PlayerData` / `SaveData` / `GameState` на все фичи.** Один класс с полями валют,
уровней, инвентаря, настроек, квестов. Ищи: класс с десятками несвязанных полей, который
инжектят почти все сервисы. Нарушены P2, P3, P4. Направление: секции сейва по модулям
(участник сейва на модуль, см. роль `save-participant` в `unity-architectures/ROLES.md`).

**U2. ScriptableObject как общая изменяемая модель.** SO, в который пишут в рантайме несколько
систем («GameData.asset»), или конфиг, совмещающий числа разных возможностей. Ищи: запись в поля
SO вне редактора, SO с полями экономики и боя вместе. P2, P3.

**U3. Синглтон-менеджер существительного.** `GameManager`, `PlayerManager`, `LevelManager`,
через которые идёт всё. Ищи: `Instance` с большим количеством входящих ссылок. P4, P19.

**U4. `PlayerPrefs` по всему коду.** Ключи читают и пишут разные классы. Инфраструктура без
владельца и скрытая общая память. P2, P5.

## Связи

**U5. Инсталлер-склейка.** Один Zenject-инсталлер/`EcsStartup`/бутстрап, где регистрируется
всё и вручную связываются модули (`a.OnX += b.Y`). Связи модулей живут вне модулей. P6, P10.

**U6. Источник знает всех получателей.** `OnLevelComplete` в одном методе зовёт награду, сейв,
аналитику, ачивки, рекламу, UI. P7. Направление — событие через шину проекта (`event-bus`).

**U7. Ссылки из инспектора поперёк модулей.** Поле `[SerializeField] ShopController` в
`QuestView`. Граф кода их не видит — ищи в `.prefab`/`.unity` по `guid` скрипта. P6, P10.

**U8. `FindObjectOfType` / `GameObject.Find` / статические события.** Скрытые зависимости,
которых нет ни в конструкторе, ни в инсталлере. P6, P10.

**U9. asmdef есть, но все ссылаются на всех.** Или одна сборка `Game` с кругом. Формальная
граница без фактической. P10.

## UI

**U10. Presenter/View как владелец логики.** Расчёт цены, проверка «можно ли купить»,
начисление награды в `MonoBehaviour` экрана. P13, P16, P18.

**U11. Страница-агрегатор.** `MainScreenPresenter` / `HudController`, инжектящий 5+ сервисов
разных возможностей и собирающий из них модель экрана. P11, P12. Направление — экран-хост со
слотами, виджеты-вклады от модулей.

**U12. Модель экрана просочилась в домен.** Доменные классы с полями «для отображения»
(`IconSprite`, `DisplayText`, `IsHighlighted`) или правила, переставленные под порядок вкладок. P12.

## Внутри модуля

**U13. God-MonoBehaviour.** Один компонент держит состояние, считает правила, сохраняет, играет
VFX и обновляет UI. P15, P19.

**U14. Правила зависят от движка.** Расчёт урона или экономики в классе, требующем `Transform`,
`Time.deltaTime`, `Resources.Load`, корутину или SDK. P16.

**U15. Сценарий в `Update`.** Оркестрация шагами-флагами в `Update` вперемешку с правилами. P17.

## ECS (LeoEcs Lite)

**U16. Компонент-свалка.** Один компонент на сущности игрока, который пишут системы разных
возможностей. P2.

**U17. Система, знающая весь мир.** Система с фильтрами по компонентам трёх-четырёх
возможностей сразу, потому что «так проще посчитать». P6, P19.

**U18. UI читает ECS-мир напрямую.** View с доступом к `EcsWorld`/пулам, а не через мост
модуля. P11, P16.

**U19. Порядок стадий как скрытая связь.** Модуль корректен, только если чужая система стоит
строго перед ним, и это нигде не выражено контрактом. P8.

## ECS (Unity DOTS / Entities)

Факты о стеке и ловушки D* — `unity-dots/DOTS_ENTITIES.md`.

**U20. Singleton-свалка.** Один singleton-компонент (`GameState`, `GameConfig`) с полями
разных возможностей, который пишут системы нескольких модулей. Тот же общий `PlayerData`, только
в мире. Ищи: `GetSingletonRW<T>` одного типа в системах разных папок. P2, P3.

**U21. Мост везде.** `World.DefaultGameObjectInjectionWorld.EntityManager` в десятке
MonoBehaviour разных фич; UI и игрок читают и пишут компоненты напрямую. Граница hybrid не
проведена, каждая фича знает внутреннее устройство мира. Ищи по `DefaultGameObjectInjectionWorld`.
P6, P16; D16.

**U22. Managed-компонент как ссылка на чужую модель.** `class : IComponentData` со ссылкой на
сервис, менеджер или Presenter другой фичи — ECS-модуль зависит от конкретного GameObject-класса.
P6.

**U23. `SystemBase`-оркестратор.** Одна managed-система, которая гоняет сценарий целиком:
читает ввод, считает правила, спавнит, пишет в UI и сейв. God-object в форме системы. P17, P19.

**U24. Логика в Baker.** Расчёты баланса, выбор вариантов, рандом, поиск по сцене внутри
`Bake`. Правило размазано между контентным пайплайном и рантаймом и не проверяется в Play.
P18; D7, D8.

**U25. `[UpdateBefore/After]` поперёк модулей.** Система фичи A ссылается атрибутом на
конкретную систему фичи B. Порядок становится скрытым контрактом, B нельзя переименовать или
разрезать без правки A. Лучше — общие группы-этапы проекта, в которые модули встают сами. P6, P8;
D15.

**U26. Компонент-событие без владельца.** Тег-событие, который добавляет одна фича, а снимают
две-три разные системы, или не снимает никто. Нет одного уборщика — нет контракта. P2, P7.

**U27. Всё в ECS или ничего.** Уникальная логика (игрок, UI, диалоги) переписана в системы ради
единообразия, или наоборот — массовые агенты на MonoBehaviour рядом с работающим ECS. Граница
hybrid проведена не по природе нагрузки. P1, P5.
