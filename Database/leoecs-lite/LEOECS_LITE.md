# LeoEcs Lite — база знаний

Факты о фреймворке и каталог ловушек. Проверено по исходникам пакета
`com.leopotam.ecslite` (Unity UPM из git; исходники — `Library/PackageCache/com.leopotam.ecslite@*/src/`:
`worlds.cs`, `components.cs`, `filters.cs`, `systems.cs`, `entities.cs`).

**Накопительная база, общая для всех проектов.** Читают `leoecs-review` и `leoecs-mechanic-integrator`; перевод механик из библиотеки — `MECHANIC-PORTING.md`. Проектная специфика (имена систем, порядок конвейера) — в `CLAUDE.md` проекта. Правила дописывания — раздел 9.

---

## 0. Что это за фреймворк и что из этого следует

Спарс-сет ECS без кодогенерации, без джобов, без бёрста. Компоненты — `struct`, доступ —
`ref` в пул по индексу сущности. Всё однопоточно и синхронно.

| Свойство | Что из этого следует |
| --- | --- |
| Проверки корректности живут под `#if DEBUG` | В плеерном билде (Release) ошибки не бросаются, а **молча портят данные**. Раздел 2 — целиком про это |
| Сущность — это `int`, индексы переиспользуются | Хранить `int` дольше кадра нельзя, только `EcsPackedEntity` (2.5) |
| Сущность без компонентов нелегальна | Пустая сущность роняет `Init`/`Run` исключением в DEBUG (2.4) |
| Пулы и фильтры резолвятся по типу компонента | Фильтр — это декларация зависимостей системы. Всё, что система `Get()`, обязано быть в фильтре (2.2) |
| Нет «сущностей-владельцев» и иерархии | Родство выражается ссылкой на packed-сущность в компоненте, а не вложенностью |

## 1. API-поверхность

Ровно то, что есть. Методов вроде `world.HasComponent<T>(entity)`, `entity.Get<T>()`, `systems.DelHere<T>()` в Lite **нет** — это API соседних фреймворков. Не вызывать по памяти.

### EcsWorld
```
int   NewEntity()                     Gen новой = 1, переиспользованной — растёт
void  DelEntity(int entity)           снимает все компоненты, потом освобождает id
EcsPool<T> GetPool<T>() where T:struct
Mask  Filter<T>() where T:struct      начало цепочки маски
short GetEntityGen(int entity)
int   GetEntitiesCount()              живые сущности мира
int   GetAllEntities(ref int[] e)
bool  IsAlive()
void  Destroy()
void  CopyEntity(int src, int dst)
```

### Mask → EcsFilter
```
Mask Inc<T>()   Mask Exc<T>()   EcsFilter End(int capacity = 512)
```

### EcsFilter
```
int   GetEntitiesCount()      ← ЕДИНСТВЕННЫЙ способ узнать число сущностей
int[] GetRawEntities()        ёмкость внутреннего массива, .Length ≠ число сущностей
Enumerator GetEnumerator()    foreach (int entity in filter)
```

### EcsPool&lt;T&gt;
```
ref T Add(int entity)     ref T Get(int entity)
bool  Has(int entity)     void  Del(int entity)
```

### Сущности вне мира
```
EcsPackedEntity world.PackEntity(int entity)          // extension
bool packed.Unpack(EcsWorld world, out int entity)    // extension: проверяет мир, живость и Gen
bool a.EqualsTo(in EcsPackedEntity b)
EcsPackedEntityWithWorld world.PackEntityWithWorld(int entity)  // если мир не под рукой
```

### Системы
```
IEcsPreInitSystem     PreInit(IEcsSystems)
IEcsInitSystem        Init(IEcsSystems)
IEcsRunSystem         Run(IEcsSystems)
IEcsPostRunSystem     PostRun(IEcsSystems)
IEcsDestroySystem     Destroy(IEcsSystems)
IEcsPostDestroySystem PostDestroy(IEcsSystems)

EcsSystems(EcsWorld defaultWorld, object shared = null)
IEcsSystems Add(IEcsSystem)   // возвращает себя, цепочка
void Init()   void Run()   void Destroy()
T GetShared<T>() where T : class
IEcsSystems AddWorld(EcsWorld world, string name)   EcsWorld GetWorld(string name = null)
```

Порядок вызовов, проверено по `systems.cs`:
- `Init()` — сначала **все** `PreInit` в порядке добавления, затем **все** `Init`.
  Не по системе целиком.
- `Run()` — все `Run` в порядке добавления, затем все `PostRun`.
- `Destroy()` — все `Destroy` в **обратном** порядке, затем все `PostDestroy` в обратном.
- Повторный `Init()` бросает `Already initialized.`; `Run()` до `Init()` —
  `Cant run without initialization.`

## 2. Семантика, которая ломает молча

Каждый пункт — расхождение DEBUG и Release: в редакторе исключение, в билде тишина и порча данных.

### 2.1. `Add` на сущность, у которой компонент уже есть
DEBUG: `Component "X" already attached to entity.`
Release: `_sparseItems[entity]` перезаписывается новым индексом, старый dense-слот **утекает**
(не попадает в recycled) и продолжает считаться занятым. Утечка памяти пула плюс потеря данных.
Перед условным `Add` — всегда `Has`.

### 2.2. `Get` на сущность без компонента
DEBUG: `Cant get "X" component - not attached.`
Release: `_sparseItems[entity] == 0`, а dense-слот 0 — **общая заглушка**, зарезервированная
конструктором пула (`_denseItemsCount = 1`). Метод вернёт `ref` на неё. Значит:
- запись уходит в никуда, но не падает;
- **все** промахнувшиеся сущности читают и пишут один и тот же экземпляр, наводки между ними;
- на экране это выглядит как «эффект иногда применяется не к тому объекту».

Отсюда правило: **всё, что система вызывает `pool.Get()`, обязано быть в её фильтре.**
Не «желательно», а условие корректности билда.

### 2.3. `Del` последнего компонента уничтожает сущность
`EcsPool.Del` в конце проверяет `componentsCount == 0` и зовёт `_world.DelEntity(entity)`.
Снятие последнего компонента = удаление сущности, `int` протухает немедленно (опасно для «сущностей-состояний» с одним тегом).

### 2.4. Сущность без компонентов нелегальна
`NewEntity()` регистрирует сущность в `_leakedEntities`; после **каждой** системы в DEBUG
идёт `CheckForLeakedEntities`, и пустая даёт
`Empty entity detected in world "default" after XxxSystem.Run().`
Правило: создал сущность — навесь первый компонент **в том же методе**,
не «в следующей системе».

### 2.5. Индексы сущностей переиспользуются, `Gen` — защита от протухания
`NewEntity` для новой сущности ставит `Gen = 1`; для переиспользованной — инвертирует
накопленный отрицательный `Gen`. Поэтому:
- хранить `int entity` в MonoBehaviour, в словаре, в компоненте — нельзя;
- собирать пакет руками (`packed.Id = entity; packed.Gen = 0;`) — нельзя: `Gen` живой
  сущности никогда не равен 0. Только `world.PackEntity(entity)`;
- `Unpack` проверяет `world != null && world.IsAlive() && живость id && Gen` — то есть сам
  прикрывает уже уничтоженный мир, отдельная проверка не нужна.

### 2.6. Проверка «фильтр пуст»
Только `filter.GetEntitiesCount() > 0`. `GetRawEntities().Length` — ёмкость массива
(стартовая 512), она положительна всегда. Такая проверка не работает никогда, и это не видно
в редакторе.

### 2.7. Изменение состава компонентов во время `foreach` по фильтру
Безопасно: на время перебора фильтр залочен, добавления и удаления копятся в `_delayedOps`
и применяются на `Dispose` энумератора. Но:
- энумератор запоминает `_entitiesCount` на входе — сущности, попавшие в фильтр внутри цикла,
  **этот кадр не обрабатываются**, только следующий;
- сущность, выпавшая из фильтра внутри цикла, всё равно будет пройдена до конца цикла —
  проверять актуальность вручную, если это важно.

### 2.8. Забытый `ref`
`var c = pool.Get(e);` компилируется и работает — копия структуры, запись теряется.
Нужен `ref var c = ref pool.Get(e);`. Компилятор молчит, тест не падает, эффект просто
«не работает». То же для `Add`: `ref var c = ref pool.Add(e);`.

## 3. Фильтры и «синглтоны»

Фильтр строится один раз в `Init` и кэшируется в поле системы; в `Run` нельзя: `End()` каждый кадр создаёт или ищет фильтр заново.

**Компоненты в одном фильтре обязаны лежать на одной сущности.** Фильтр
`Inc<PlayerTag>().Inc<Door>()` не совпадёт никогда (типовая ошибка перехода с ООП). Данные на разных сущностях — два фильтра.

Чтение «синглтона» (сущность, которой по построению одна — игрок, камера, настройки мира):
```csharp
if (_playerFilter.GetEntitiesCount() == 0) { return; }
int player = _playerFilter.GetRawEntities()[0];
```
`GetRawEntities()[0]` законен только после проверки счётчика.

Пара фильтров вместо ветвления — реакция на смену состояния:
```csharp
_needEnable  = world.Filter<Focused>().Inc<Refs>().Exc<Applied>().End();
_needDisable = world.Filter<Applied>().Inc<Refs>().Exc<Focused>().End();
```
Система работает только в кадры, когда что-то изменилось; `if` внутри нет.
**Фильтр уборки должен быть шире или равен фильтру выдачи**, никогда не уже: иначе объект,
потерявший входное условие, залипнет в применённом состоянии навсегда.

## 4. Стадии конвейера

Деление систем — по стадиям кадра, не по фичам и не по «читает/пишет» (читают и пишут все).
Порядок добавления в `EcsSystems` — это контракт кадра, его нельзя менять «чтобы красивее».

| Стадия | Что делает | Знает про Unity |
| --- | --- | --- |
| Input | читает устройства и сервисы ввода → пишет в компоненты | да |
| Simulation | правила игры: считает и применяет состояние мира | **нет** — этот слой переезжает в следующий проект как есть |
| Presentation | состояние мира → визуал, звук, трансформы, накопители камеры | да |
| Debug | гизмо, отладочные окна, `EcsWorldDebugSystem` | да, только редактор |
| Cleanup | снятие однокадровых компонентов | нет |

Simulation остаётся переносимым, пока в нём нет `Transform`, `Camera`, `Physics`.

Внутри Simulation действует правило «считающие до применяющей»: несколько систем считают
вклады в компоненты, **одна** применяет во внешний мир (один `CharacterController.Move` за кадр,
два дают дрожь на склонах).

## 5. Паттерны

### 5.1. Накопитель презентации
Два слоя состояния, их нельзя путать:
- **состояние симуляции** — живёт долго, пишется геймплеем, не обнуляется (страх, ранение,
  выносливость). По одному мелкому компоненту на состояние, не толстый `PlayerState`;
- **накопитель презентации** — обнуляется каждый кадр отдельной `Clear`-системой в начале
  стадии, вкладчики только прибавляют (`+=`), применяет ровно один `Apply` в конце.

Обнуление — **отдельной** системой, не внутри применяющей: иначе вкладчик после `Apply` молча копит, а в инспекторе ноль вместо итога.

Не всё складывается одинаково: смещения суммируются, веса нормализуются, частота шума вообще
не аддитивна (два источника по 1 не должны дать 2) — для неё `Max`.

Мост между слоями — система вида «читает состояние симуляции, прибавляет в накопитель».

### 5.2. Однокадровый компонент (событие)
Вешается на сущность, **к которой относится событие**, а не на инициатора: тогда фильтры вида
`Inc<InteractionRequest>().Inc<DoorTag>()` работают напрямую, а полиморфизм получается
композицией компонентов — без `switch` и без наследования.

Снимает такой компонент **одна система-уборщик в конце тика**, а не потребители. Иначе:
второй потребитель падает на повторном снятии, а необработанный запрос повисает навсегда.

### 5.3. Кнопка — событие, а не состояние
Нужен фронт (сравнение с прошлым кадром), иначе действие срабатывает каждый кадр удержания.
Приватное поле в системе тут допустимо — это состояние устройства ввода, одно на игру,
а не состояние сущности. Считать фронт **до** цикла по сущностям, иначе первая сущность
съест его у остальных.

Ловушка Unity Input System: у действия из шаблона может стоять интеракция `Hold` — тогда
`performed` приходит только после удержания, и быстрое нажатие теряется.

### 5.4. Authoring: сцена → данные
MonoBehaviour на объекте сцены рождает сущность в `Start`, кладёт ссылки на Unity-объекты
в компонент-мост (`<Что>Refs`) и заливает настройки из конфига в компоненты.

Заливать настройки из `ScriptableObject` в компонент при рождении **лучше**, чем передавать SO в конструктор системы: система без Unity-зависимостей, второй сущности можно дать свои числа, конфиг читается один раз.

Authoring обязан удалить сущность в `OnDestroy` — иначе сущности утекают при уничтожении
объектов сцены. `Unpack` сам прикроет уже уничтоженный мир:
```csharp
private void OnDestroy() {
    if (_packed.Unpack(_worldProvider.World, out int entity)) { _worldProvider.World.DelEntity(entity); }
}
```

Authoring — единственное место, где законно **читать** `Transform`: один раз, при рождении,
забирая то, что расставил дизайнер. Дальше `Transform` — только выход конвейера.

Общий authoring с абстрактным наследником (базовый создаёт сущность и общие компоненты,
наследник дописывает своё) — законен: это код сборки, а не логика времени выполнения,
готовая сущность по-прежнему без наследования.

### 5.5. Мост «коллайдер → сущность»
Рейкаст даёт `Collider`; коллайдеры часто висят на детях, поэтому
`hit.collider.GetComponentInParent<TAuthoring>()`, а authoring хранит `EcsPackedEntity`.

## 6. Каталог ловушек для ревью

Нумерация стабильна — на неё ссылается агент `leoecs-review`. Отсортировано по цене ошибки.

**Молчаливая порча данных**
- **L1** `pool.Get()` компонента, которого нет в фильтре системы → в билде общая заглушка (2.2)
- **L2** Забытый `ref` у `Get`/`Add` → работа с копией структуры (2.8)
- **L3** `Add` без проверки `Has` там, где компонент может уже быть (2.1)
- **L4** Проверка пустоты фильтра через `GetRawEntities().Length` (2.6)
- **L5** Хранение `int entity` вне кадра вместо `EcsPackedEntity`; сборка пакета руками (2.5)
- **L6** Потерянное возвращаемое значение чистой функции (`Vector3.ClampMagnitude`,
  `Mathf.Repeat`, `.normalized`) — посчитал и выбросил
- **L7** Поле настройки, забытое при заливке из конфига → 0 → деление на ноль → `NaN`.
  `NaN` не бросает исключений, тихо расползается по конвейеру и убивает трансформ.
  Проверять надо и код, и значение в самом `.asset`: `default` в C# не действует
  на уже созданный ассет

**Структурные ошибки**
- **L8** Фильтр из компонентов, лежащих на разных сущностях (раздел 3)
- **L9** Состояние сущности в приватном поле системы вместо компонента: второй сущности
  не дать своего значения, извне (катсцена, скрипт) не задать. Исключение — состояние
  устройства ввода (5.3)
- **L10** Однокадровый компонент снимается потребителем, а не уборщиком (5.2)
- **L11** Фильтр уборки уже фильтра выдачи → залипшее состояние (раздел 3)
- **L12** Построение фильтра или `GetPool` в `Run` вместо `Init`
- **L13** Сущность создана без единого компонента (2.4)
- **L14** Authoring без `OnDestroy` → утечка сущностей
- **L15** Событие повешено на инициатора вместо цели (5.2)
- **L16** Снятие последнего компонента как «сброс состояния» → сущность уничтожена (2.3)

**Конвейер и порядок**
- **L17** Две системы применяют одно и то же во внешний мир (два `Move` за кадр)
- **L18** Считающая система стоит после применяющей
- **L19** Вкладчик в накопитель стоит после `Apply` → молча копит (5.1)
- **L20** Обнуление накопителя внутри `Apply`, а не отдельной системой (5.1)
- **L21** Unity-типы (`Transform`, `Camera`, `Physics`; `Time` кроме `deltaTime`)
  в Simulation-системе → слой перестал быть переносимым (раздел 4)
- **L22** Чтение `Transform` как входа: те же данные уже есть в компонентах. Единственный
  законный обратный поток — `isGrounded` от физики. Исключение — authoring (5.4)
- **L23** Кнопка обрабатывается по состоянию, без фронта (5.3)

**Unity-специфика**
- **L24** `#if UNITY_EDITOR` разрывает одно выражение (цепочку `.Add(...)`) или обёрнут
  вызов при незавёрнутом теле метода: в редакторе соберётся, плеерный билд сломается.
  Директива должна вырезать **место, где упомянут** Editor-only тип
  (`Leopotam.EcsLite.UnityEditor.*` лежит в Editor-сборке)
- **L25** Чтение кватерниона по компонентам (`.y` — это не градусы). Поворот «от исходного» —
  умножением `исходный * Quaternion.Euler(...)`, порядок важен
- **L26** Чтение трансформа → прибавление → запись обратно: накопление, объект укатится.
  Нужна абсолютная запись от базового значения
- **L27** `CharacterController.isGrounded` прочитан **до** `Move` — недостоверен
- **L28** Движущийся коллайдер без кинематического `Rigidbody`: PhysX каждый кадр
  перестраивает статическое дерево
- **L29** Магическое число слоя или тега (`gameObject.layer = 6`) вместо константы
  либо `LayerMask.NameToLayer`
- **L30** Тяжёлый поиск (`GetComponentInParent`, `FindObjectOfType`) в `Run` каждый кадр
  там, где результат можно закэшировать при рождении сущности

**Конвенции проекта** (проверяются по `CLAUDE.md` проекта, не по этой базе)
- **L31** Namespace не зеркалит путь папки; файл лежит не в своей папке
- **L32** Имя не по схеме проекта (`<Noun>Tag` — что это навсегда; причастие — временное
  состояние; `<Что>Refs` — мост в MonoBehaviour-мир; система — глагол плюс `System`)
- **L33** Система делает больше одного преобразования (в имени напрашивается «и»)
- **L34** Преждевременное обобщение: общий компонент-мост «на будущее», когда вторая
  сущность ещё не появилась

## 7. Интеграция с Unity и Zenject

Проверенная связка:
- `IEcsWorldProvider` — владелец единственного `EcsWorld`, регистрируется в DI как синглтон;
- `EcsStartup` реализует `IInitializable` (собирает системы и зовёт `Init`), `ITickable`
  (`Run`), `IDisposable` (`Destroy` систем, затем `World.Destroy()` — именно в этом порядке);
- сборка систем — методами по стадиям (`AddInputSystems`, `AddSimulationSystems`, …),
  а не по фичам;
- authoring-MonoBehaviour получают `IEcsWorldProvider` через `[Inject]`, поэтому сцена
  должна биндиться контекстом, в котором провайдер виден.

Отладка в редакторе: `Leopotam.EcsLite.UnityEditor.EcsWorldDebugSystem` и `EcsSystemsDebugSystem`
из пакета `com.leopotam.ecslite.unityeditor` — Editor-only сборка, см. L24. Версия 2025.11.5 на
Unity 6.6 не компилируется (CS0619 `EndNameEditAction` в `TemplateGenerator.cs`) — на 6.6+ пакет
не ставить, пока не выйдет исправленная. Причина: `EndNameEditAction` помечен obsolete, замена —
`AssetCreationEndAction` (`EntityId` вместо `int`). По трекеру Unity (issuetracker.unity.com/issues/22524)
ошибка воспроизводится с 6000.5.0b1 и 6000.6.0a, на 6000.4.11 — нет; в самом Unity исправлено в
6000.5.4f1 и 6000.6.0b4. Последний релиз `ecslite-unityeditor` — 2025.11.5, фикса в нём нет.
Пакет безопасен на 6.4 и ниже; 6.5+ проверять отдельно.

Authoring-объекты сцены умирают раньше или позже её мира недетерминированно — поэтому `Unpack` в `OnDestroy` обязателен (5.4).

---

## 8. Чего в Lite нет (не выдумывать)

- нет систем-групп с условным выполнением — только линейный список;
- нет `IEcsFilterSystem`, автосоздания фильтров по атрибутам и инъекции полей — всё руками
  в `Init` (это делают сторонние расширения, не ядро);
- нет реактивных фильтров «по добавлению/удалению» в базовом виде: есть события за
  `LEOECSLITE_FILTER_EVENTS` и `LEOECSLITE_WORLD_EVENTS`, паттерн по умолчанию — пара
  фильтров с `Exc<>` (раздел 3);
- нет многопоточности и джобов;
- нет сериализации мира.

## 9. Правила дописывания этой базы

- Сюда — **факты**: API, семантика, ловушки, паттерны. Процедура ревью — в `~/.claude/agents/Unity ECS/leoecs-review.md`, не дублировать.
- Новая ловушка получает **следующий свободный номер** (L35, L36, …). Номера не
  переиспользуются и не перенумеровываются — на них ссылаются отчёты ревью.
- Ловушка: что написано → DEBUG → Release → как правильно.
- Поведение фреймворка проверяется по исходникам в `PackageCache`, со ссылкой на файл; не по памяти.
- Проектные имена допустимы только как пример; правило формулируется в общем виде.
