# Перевод механики из библиотеки в LeoEcs Lite

Факты для `leoecs-mechanic-integrator`: как механика из `MECHANICS/` (роли из `unity-architectures/ROLES.md`, код `TEMPLATES/` под Zenject + MVP) становится компонентами и системами. Семантика и ловушки L1… — `LEOECS_LITE.md` (здесь только ссылки). Профиль архитектуры — `unity-architectures/LEOECS-LITE.md`.

## 0. Что переносится, а что пишется заново

| Из записи | В ECS | Как |
|---|---|---|
| «Ядро правила», граничные случаи, «Известные грабли» | Simulation-системы | **переносится смысл**, код переписывается |
| «Правило против контента», поля конфига | SO + компоненты-настройки | конфиг переносится как есть, заливка в компоненты — новая |
| сервис с полями состояния | компоненты | пишется заново |
| методы сервиса | системы или компонент-запрос + система | пишется заново |
| `ReactiveProperty`, MessagePipe | компонент-состояние, однокадровый компонент | пишется заново |
| View, Presenter, страницы | остаются в MVP-слое проекта, если он есть | не трогается |
| «Проверка после подключения» | чек-лист, плюс проверки ECS | переносится, дополняется |

Код `TEMPLATES/` — справочник по правилу, не исходник для копирования. Класс сервиса целиком в ECS-проекте, дергаемый из системы, — не перевод: состояние вне мира, фильтры и сейв мира его не видят.

Исключение — чистые функции без состояния (формула, кривая, проверка соседства в сетке): переносятся `static`-методами.

## 1. Состояние → компоненты

- Одно поле-смысл — один маленький компонент, не толстый `XxxState` (`LEOECS_LITE.md` §5.1).
- Состояние «на объекте» (клетка сетки, враг) — компонент на его сущности.
- Состояние «на всю игру» (счётчик волны, открытые слоты) — компонент на сущности-синглтоне;
  чтение по правилу §3, `GetRawEntities()[0]` только после проверки счётчика.
- Коллекции в сервисе (`List<Item>`) → сущности с компонентом-меткой; обход — фильтром.
  Порядок, если важен, — полем-индексом в компоненте, а не порядком фильтра.
- Ссылка на другой объект → `EcsPackedEntity` в компоненте, не `int` (§2.5).

## 2. Методы правила → системы

| Метод сервиса | В ECS |
|---|---|
| вызывается каждый кадр / по тику | Run-система Simulation со своим фильтром |
| вызывается снаружи по действию (`TryMerge(a, b)`) | однокадровый компонент-запрос на целевой сущности + система, которая его обрабатывает |
| возвращает результат вызывающему | результат — однокадровый компонент на той же сущности; вызывающий читает его в следующей по порядку системе |
| проверка «можно ли» перед действием | фильтр с `Exc<>` или компонент-блокировка, а не `if` в каждом потребителе |
| таймер на `SecondTick` | компонент-счётчик, уменьшается на `deltaTime` одной системой; срабатывание — однокадровый компонент |

Несколько систем считают, одна применяет (§4). Если метод сервиса и считал, и применял —
это две системы.

## 3. События и состояние

- Сообщение MessagePipe → однокадровый компонент на сущности, к которой событие относится
  (§5.2). Снимает одна Cleanup-система в конце тика.
- `ReactiveProperty` → обычный компонент. Если снаружи мира (UI, мета на Zenject) кто-то
  подписан на значение, Presentation-система публикует изменение в R3/MessagePipe проекта —
  мир не держит подписчиков.
- Событие, на которое реагирует мета-слой вне ECS (выдать награду в кошелёк) —
  Presentation-система на однокадровом компоненте вызывает сервис меты или публикует
  его сообщение. Обратное направление — см. §6.

## 4. Провайдеры (`external-provider`)

| Что спрашивает механика | В ECS |
|---|---|
| значение на конкретном объекте (шанс, множитель этого врага) | компонент на сущности, заливается authoring'ом |
| значение из глобального источника (множитель от апгрейдов меты) | shared-данные `EcsSystems` или сервис в конструктор системы; система остаётся без Unity-типов |
| решение «можно ли» от проекта | компонент-блокировка, который ставит проектная система, или `Exc<>` в фильтре |

Сервис в конструкторе системы допустим, если он не Unity-объект и не SO — иначе Simulation
перестаёт переноситься (§4, §5.4).

## 5. Тик, ввод, конфиг

- Тик — стадия, в которую добавлена система. Секундные таймеры — §2.
- Ввод — Input-система пишет компонент-намерение; правило его читает. Фронт кнопки — до
  цикла по сущностям (§5.3).
- Конфиг — SO читается authoring'ом или init-системой при рождении сущности (§5.4). Если
  в проекте есть Zenject-фундамент, SO берётся из `GameConfigs` и передаётся в authoring
  инъекцией, в систему — нет.

## 6. UI и мета

UI в ECS-проекте обычно остаётся в MVP-слое. Мост в обе стороны:

- мир → UI: Presentation-система публикует изменения (см. §3), Presenter подписан на них;
- UI → мир: кнопка страницы через Presenter создаёт однокадровый компонент-запрос
  (через сервис-фасад, который знает `IEcsWorldProvider`), дальше обрабатывает система.
  Presenter мир напрямую не держит.

Если мета-механика целиком живёт в Zenject-слое (кошелёк, магазин) — её в ECS не переводят:
её встраивает `unity-mechanic-integrator`, а геймплей связывается с ней мостом из §3.

## 7. Сейв

В Lite нет сериализации мира (§8 базы). Схема:

- участник сейва — вне мира (`ISaveParticipant` в Zenject-фундаменте или аналог проекта),
  хранит DTO;
- `Restore` пишет только в DTO: при загрузке на старте мира ещё может не быть;
- init-система механики при создании мира рождает сущности из DTO; DTO пуст — дефолт из
  конфига;
- `Capture` снимает снимок фильтрами, пока мир жив; уничтожение мира (выгрузка сцены)
  предваряется снимком — иначе последний прогресс теряется;
- в DTO не хранятся `int`-сущности и `EcsPackedEntity`: при загрузке они другие. Связи —
  через стабильные идентификаторы из данных механики.

## 8. Authoring и сцена

По разделу «Сцена и префабы» записи: каждый требуемый объект сцены — authoring, рождающий
сущность в `Start`, `<Что>Refs` для Unity-ссылок, удаление в `OnDestroy` через `Unpack`
(§5.4). Коллайдер → сущность — §5.5.

## 9. Порядок в конвейере

Для каждой новой системы — стадия и место внутри неё с обоснованием:

- Input: чтение ввода механики;
- Simulation: запросы → проверки → считающие → одна применяющая;
- Presentation: фидбек, мост в UI и мету;
- Cleanup: уборщики однокадровых компонентов механики — по одному на тип.

Порядок существующих систем проекта не меняется «для красоты»: это контракт кадра.

## 10. Грабли перевода

- Сервис скопирован как есть и вызывается из системы → состояние вне мира, сейв и
  фильтры его не видят.
- Запрос обработан в той же системе, что его создала, — порядок внутри кадра неочевиден,
  при переносе системы в другую стадию ломается.
- Результат действия читается раньше системы, которая его пишет → эффект на кадр позже,
  «ватный» отклик. Сверить с `gamecraft/FEEDBACK.md`. Родственник L18.
- Коллекция из сервиса переведена в `List` внутри компонента → копии структуры делят один
  список, а соседние поля-значения без `ref` правятся в копии (L2). Коллекции — сущностями (§1).
- Уборщик однокадрового компонента поставлен до его потребителя → событие не доходит ни до
  кого. Обратная ошибка — снятие потребителем (L10).
- Ссылка между объектами механики сохранена как `int` в компоненте или в DTO сейва → после
  удаления или загрузки указывает на чужую сущность (L5).
