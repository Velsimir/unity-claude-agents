# Профиль архитектуры: LeoEcs Lite (+ Zenject снаружи)

Геймплей на LeoEcs Lite: состояние в компонентах-`struct`, логика в системах, конвейер стадий в
`EcsStartup`. Мета-слой, сейвы и UI обычно остаются на Zenject + MVP — для них `ZENJECT-MVP.md`
или профиль DI проекта.

Факты о фреймворке — `~/.claude/Database/leoecs-lite/LEOECS_LITE.md` (ловушки L1…), перевод
механики в ECS — `~/.claude/Database/leoecs-lite/MECHANIC-PORTING.md`. Здесь только признаки и
сопоставление ролей.

Встраивает агент `leoecs-mechanic-integrator`, не `unity-mechanic-integrator`.

## Признаки

| Признак | Где смотреть | Вес |
|---|---|---|
| пакет `com.leopotam.ecslite` | `Packages/manifest.json` | решающий |
| `EcsWorld`, `EcsSystems`, `IEcsRunSystem` / `IEcsInitSystem` | код | решающий |
| класс-точка входа, собирающий системы (`EcsStartup` или аналог) | код | решающий |
| `IEcsWorldProvider` или иной владелец мира в DI | код, инсталлеры | поддерживающий |
| authoring-`MonoBehaviour`, создающие сущности в `Start` | код, сцены | поддерживающий |
| `com.leopotam.ecslite.unityeditor` | `Packages/manifest.json` | поддерживающий |

Уверенный вывод: пакет + `EcsSystems` + точка входа конвейера. Отдельно фиксируется, что снаружи
ECS: Zenject-фундамент, свой DI или ничего — от этого зависят `config`, `save-participant`,
`ui-entry`.

Легко спутать: Unity Entities (DOTS, `com.unity.entities`) и другие ECS (Morpeh, Arch, LeoEcs
Proto) — **не** этот профиль, другая семантика мира и систем.

## Роли → реализация

| Роль | Реализация | Где подробно |
|---|---|---|
| `code-home` | папка фичи в дереве ECS-кода проекта — компоненты, системы, authoring рядом; точная конвенция — из `CLAUDE.md` проекта | `CLAUDE.md` проекта |
| `service-registration` | правило механики — не сервис, а набор систем, добавленных в `EcsStartup` в методы нужных стадий; сервис-синглтон остаётся только для того, что живёт вне мира (сейв, мета) | `LEOECS_LITE.md` §4, §7 |
| `config` | `ScriptableObject` читается authoring'ом или init-системой при рождении сущности и заливается в компоненты; система SO в конструктор не получает | `LEOECS_LITE.md` §5.4 |
| `save-participant` | в мире сериализации нет: отдельный участник сейва снаружи ECS держит DTO; при загрузке init-система рождает сущности из DTO, при сохранении участник снимает снимок фильтрами | `MECHANIC-PORTING.md` «Сейв» |
| `ui-entry` | UI остаётся в MVP-слое проекта; мост — компонент-запрос от кнопки или сервис-фасад, который читает мир | `MECHANIC-PORTING.md` «UI и мета» |
| `presentation-binding` | Presentation-системы: состояние мира → трансформы, визуал; `<Что>Refs`-компонент держит ссылки на Unity-объекты | `LEOECS_LITE.md` §4, §5.4 |
| `state-stream` | нет реактивных свойств: текущее значение — компонент; кто снаружи мира хочет наблюдать — Presentation-система публикует в R3/MessagePipe проекта | `MECHANIC-PORTING.md` «События и состояние» |
| `event-bus` | однокадровый компонент на сущности, к которой относится событие; снимает одна Cleanup-система в конце тика | `LEOECS_LITE.md` §5.2 |
| `tick` | `EcsStartup.Run` из `ITickable` или `Update`; секундный таймер — компонент-счётчик с `deltaTime`, а не отдельный тик | `LEOECS_LITE.md` §7 |
| `input` | Input-стадия: система читает устройство или сервис ввода и пишет в компоненты; фронт кнопки считается до цикла по сущностям | `LEOECS_LITE.md` §5.3 |
| `external-provider` | провайдер из записи механики → компонент с данными на сущности или shared-сервис, переданный в систему через `EcsSystems` shared / конструктор | `MECHANIC-PORTING.md` «Провайдеры» |
| `feedback-hook` | Presentation-система на однокадровых компонентах-событиях запускает VFX, звук, анимацию | `LEOECS_LITE.md` §5.1, §5.2 |
| `lifetime` | мир живёт со сценой или с проектом — по проекту; authoring удаляет сущность в `OnDestroy` через `Unpack` | `LEOECS_LITE.md` §5.4, §7 |
| `layer-boundary` | Simulation-системы не трогают `Transform`, `Camera`, `Physics`, `UnityEngine.Object`; Unity только в Input и Presentation | `LEOECS_LITE.md` §4 |

## Адаптация кода из библиотеки

`TEMPLATES/` не копируются — механика **переводится**: состояние сервиса → компоненты, методы
правила → системы Simulation, сообщения → однокадровые компоненты. Процедура и таблица —
`leoecs-lite/MECHANIC-PORTING.md`.

## Проверки после встраивания

- ноль ошибок компиляции;
- новые системы добавлены в свою стадию, порядок внутри стадии обоснован;
- у каждого однокадрового компонента ровно один уборщик в Cleanup;
- каждая `Get`/`ref` в системе покрыта её фильтром;
- в Simulation нет `UnityEngine`-типов, кроме математики;
- authoring удаляет свои сущности в `OnDestroy`;
- Play Mode в Development-билде или редакторе с `DEBUG` — без исключений LeoEcs;
- после — ревью агентом `leoecs-review`.

## Грабли

Полный каталог — `LEOECS_LITE.md` §6. При встраивании механики чаще всего:

- событие снимают потребители, а не одна Cleanup-система → второй потребитель падает;
- компоненты «одного объекта» разнесены по разным сущностям, а фильтр ждёт их вместе →
  фильтр пуст всегда;
- `int`-сущность хранится в сервисе мета-слоя дольше кадра → протухает, нужен `EcsPackedEntity`;
- сейв восстанавливается раньше, чем создан мир → данные теряются, нужен DTO и init-система.
