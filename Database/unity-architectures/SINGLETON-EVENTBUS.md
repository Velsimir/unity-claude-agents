# Профиль архитектуры: SINGLETON-EVENTBUS

MonoBehaviour-синглтоны-менеджеры на сценах плюс статическая шина событий на интерфейсах.
Без DI-контейнера и ECS. Типично для старых, купленных и быстро собранных мобильных проектов.

## Признаки

| Признак | Где смотреть | Вес |
|---|---|---|
| нет `com.svermeulen.extenject`/Zenject, VContainer, LeoEcs, Entities | `Packages/manifest.json`, `Assets/Plugins` | решающий |
| много `public static <T> Instance` в MonoBehaviour-менеджерах (`*Manager`, `SaveLoad`, `Global`) | код | решающий |
| статический класс шины с `Subscribe/Unsubscribe/RaiseEvent` по интерфейсу-маркеру подписчика | код | решающий |
| интерфейсы событий вида `I*Handler : I<маркер>` | код | поддерживающий |
| `DontDestroyOnLoad` на глобальных менеджерах загрузочной сцены | код, первая сцена | поддерживающий |
| сейв одним классом-менеджером с DTO (SaveGameFree, PlayerPrefs, JSON в файл) | код | поддерживающий |
| ссылки на окна и менеджеры выставлены в инспекторе | сцены | поддерживающий |

Минимум для уверенного вывода: отсутствие DI/ECS + синглтоны-менеджеры + статическая шина.

С чем спутать: «синглтоны без шины» — события через C#-`event`/`UnityEvent` на менеджерах. Роли те же, кроме `event-bus` (там `event` у менеджера-источника); шины нет вовсе — пометь отличие в блоке `## Архитектура` проекта, отдельный профиль не нужен.

## Роли → реализация

| Роль | Реализация | Пример строки или ссылка на базу |
|---|---|---|
| `code-home` | в существующий корень кода проекта, папкой по механике; неймспейс и asmdef — только если проект ими пользуется | `Assets/<корень>/<Mechanic>/` |
| `service-registration` | MonoBehaviour-синглтон `public static <T> Instance { get; private set; }`, присваивается в `Awake`, дубль уничтожается; объект на нужной сцене | `if (Instance != null && Instance != this) { Destroy(gameObject); return; } Instance = this;` |
| `config` | ScriptableObject, ссылка `[SerializeField]` на синглтоне механики | `[SerializeField] private <Mechanic>Config m_config;` |
| `save-participant` | новое поле/секция в DTO сейв-менеджера проекта + чтение в `Load`, запись в `Save`; ключ — имя поля. Порядок: механика читает состояние у сейв-менеджера в `Start`, после его `Awake` | поля в `SaveLoad.CustomData`-подобном классе |
| `ui-entry` | окно — MonoBehaviour на канвасе сцены, открытие `SetActive(true)` или методом окна; кнопку и ссылку на окно владелец ставит в инспекторе | `<Mechanic>Window.Show()` |
| `presentation-binding` | View подписывается на событие шины (или `event` менеджера) и читает текущее значение у синглтона; ввод — прямой вызов метода синглтона | `OnEnable: EventBus.Subscribe(this)` |
| `state-stream` | отдельного механизма нет: свойство на синглтоне + событие изменения через шину | `int Balance { get; }` + `I<Mechanic>ChangedHandler` |
| `event-bus` | интерфейс `I<Event>Handler : I<маркер>` с методом-обработчиком, публикация через статическую шину проекта | `EventBus.RaiseEvent<I<Event>Handler>(h => h.On<Event>(...))` |
| `tick` | `Update`/`FixedUpdate` синглтона механики или корутина; для секундных тиков — `InvokeRepeating`/корутина | `IEnumerator TickRoutine()` |
| `input` | как в проекте: старый `Input`, джойстик-плагин или кнопки UI; правило получает уже готовое действие методом | `PlayerController` → `<Mechanic>.Instance.Do()` |
| `external-provider` | интерфейс провайдера + `[SerializeField] MonoBehaviour` с реализацией или статическое свойство, которое проект выставляет при старте | `[SerializeField] private MonoBehaviour m_providerBehaviour;` |
| `feedback-hook` | подписчик на событие шины рядом с View (DOTween, звук, VFX); правило подачу не знает | `I<Event>Handler` на объекте эффектов |
| `lifetime` | глобальное — `DontDestroyOnLoad` на загрузочной сцене; сценовое — живёт с объектом сцены. Отписка от шины в `OnDisable`/`OnDestroy` обязательна | `OnDisable: EventBus.Unsubscribe(this)` |
| `layer-boundary` | слоёв нет; минимум, который держим сами: правило механики не ссылается на View и окна, View не меняет состояние в обход методов синглтона | Grep `<Mechanic>Window` в файле правила — пусто |

## Адаптация кода из библиотеки

Код в `MECHANICS/*/TEMPLATES/` написан под Zenject-фундамент:

- сервис с `[Inject]`-конструктором → MonoBehaviour-синглтон, зависимости — через `Instance`
  других менеджеров или `[SerializeField]`;
- инсталлер и биндинги — удаляются, вместо них объект на сцене;
- `ReactiveProperty`/R3 → свойство + событие шины (R3 оставить, только если пакет уже в проекте);
- MessagePipe → интерфейс-обработчик на шине проекта;
- `ISaveParticipant` → поля в DTO сейв-менеджера и две строки в его `Save`/`Load`;
- UniTask — оставить, если пакет есть, иначе корутины.

Ядро правила (расчёты, условия, конфиг) переносится как есть.

## Проверки после встраивания

- ноль ошибок компиляции;
- у каждого `Subscribe` есть парный `Unsubscribe` (Grep по классу);
- синглтон механики на нужной сцене ровно один; второй экземпляр уничтожается;
- порядок инициализации: никто не обращается к `Instance` механики в `Awake` раньше, чем она
  его присвоила (обращения — в `Start`/`OnEnable` после загрузки сцены);
- новое поле сейва переживает перезапуск и не ломает старый сейв (дефолт при отсутствии);
- ручные шаги в инспекторе перечислены списком: объект на сцене, ссылки на окно и конфиг.

## Грабли

- обращение к `X.Instance` в `Awake` другого объекта → `NullReferenceException` по случайному
  порядку `Awake`;
- забытая отписка от статической шины → после перезагрузки сцены вызов на уничтоженном объекте
  (`MissingReferenceException`) и утечка;
- синглтон со сцены локации помечен `DontDestroyOnLoad` → при возврате на сцену два экземпляра;
- новое поле в DTO сейва без дефолта → старые сейвы грузят ноль/`null`, у игроков обнуляется
  прогресс механики;
- ссылка из инспектора не выставлена → механика молча не работает; агент этого не видит, только ручной шаг владельца.
