# Разведка архитектуры Unity-проекта

Один вопрос: по какому профилю из `Database/unity-architectures/` встраивать код в проект.
Проект не меняет — единственная запись это блок в `CLAUDE.md` проекта, с согласия владельца.

## Прочитай перед работой

- `~/.claude/Database/unity-architectures/ROLES.md` — роли, по которым сравниваешь.
- Раздел «Признаки» каждого профиля в `~/.claude/Database/unity-architectures/`
  (все `*.md`, кроме `ROLES.md` и `_TEMPLATE.md`). Список не зашит: новый файл в папке — сразу
  кандидат.
- `~/.claude/Database/codegraph/CODEGRAPH.md` — если в корне проекта есть `.codegraph/`.

## Шаг 0. Уже известно?

В `CLAUDE.md` проекта есть `## Архитектура` — проверь один-два решающих признака профиля.
Совпали — верни блок как есть, без разведки. Не совпали (другой DI, добавился ECS) — продолжай
и в конце предложи обновить блок.

## Шаг 1. Собери сигналы

Дёшево и по порядку — большинство проектов определяются на первых двух:

1. `Packages/manifest.json` — DI, ECS, реактивщина, UI Toolkit, Input System.
2. Точка входа: инсталлеры, `EcsStartup`, bootstrapper, `[RuntimeInitializeOnLoadMethod]`,
   первая сцена в `EditorBuildSettings.asset`.
3. Корень кода и слои: фактическое дерево `Assets/**/*.cs` без `Plugins/`, `ThirdParty/`,
   `Library/`, сгенерированного кода; asmdef.
4. По каждой роли из `ROLES.md` — как её решает проект: `codegraph explore` по именам вроде
   `Save`, `Install`, `Page`, `Tick`, `Publish`; без графа — Grep.
5. Синглтоны и статические точки доступа (`Instance`, `static ... Current`) — признак
   архитектуры без DI.

Роль, решённая в инспекторе (UI-менеджер на объекте сцены), видна только в YAML сцены или через
Unity MCP — граф её не видит.

## Шаг 2. Сопоставь с профилями

По каждому профилю: какие решающие «Признаки» совпали, какие нет.

- **Ровно один профиль, все решающие признаки** — вывод уверенный.
- **Два профиля на разные слои** (Zenject-мета + ECS-геймплей) — норма: оба, с границей, какой
  слой по какому профилю.
- **Частичное совпадение** — не округляй до ближайшего: что совпало, что нет, спроси владельца.
- **Ни одного** — архитектура новая. Опиши по ролям, что нашёл, предложи завести профиль
  `Database/unity-architectures/<ARCH-NAME>.md` по `_TEMPLATE.md` (и строку в `INDEX.md` по
  правилу `library-index`). Без согласия не пишешь. Отказ — работа идёт по описанию из блока
  `## Архитектура`, без профиля.

## Шаг 3. Результат

Блок для `CLAUDE.md` проекта, одна страница максимум:

```markdown
## Архитектура

Профиль: `<ARCH>` (`~/.claude/Database/unity-architectures/<ARCH>.md`)
[Для гибрида: мета/UI/сейвы — `<ARCH-1>`, геймплей — `<ARCH-2>`.]
Корень кода: `<путь>`. Неймспейс: `<корень>`.

Отличия от профиля:
- <роль>: <как в этом проекте, если расходится с профилем>
```

Только отличия, не пересказ профиля. Нет отличий — «Отличий нет».

Записать блок:
- `CLAUDE.md` есть — покажи блок и спроси, дописать ли.
- `CLAUDE.md` нет — по правилу `~/.claude/rules/project-claude-md/project-claude-md.md`
  спроси, заводить ли файл; разведка — его раздел «Архитектура».
- Отказ — верни блок вызвавшему агенту текстом, в файл не пиши.

## Кто пользуется

- `unity-mechanic-integrator`, `leoecs-mechanic-integrator` — первым шагом: куда и как встраивать.
- `unity-mechanic-auditor` — отделить ядро проекта от механик при оценке переносимости.
- `architecture-review` — профиль как «что здесь принято» перед критикой границ.

## Чего не делать

- Не менять код, сцены, пакеты — только блок в `CLAUDE.md` и только с согласия.
- Не выдавать частичное совпадение за уверенный вывод.
- Не заводить профиль в библиотеке без согласия владельца.
- Не вписывать в профиль имена проекта-донора — только общие имена фреймворка.
